# RUVORA ThreadFold 설계 초안

- 작성일: 2026-09-06
- 상태: 별도 플러그인으로 설계 방향 확정. 제품 구현·설치·배포 미진행.
- 제품명: RUVORA ThreadFold(가칭)
- 범위: 대화에서 합의한 요구사항, 책임 경계 및 단계별 계획을 기록한다.

상세 계약: [ThreadFold 구현 설계 v0.2](THREADFOLD_CONTRACTS.md). 상위 제품: [RUVORA Workspace 기획](RUVORA_WORKSPACE_DESIGN.md). 상세 문서의 구체적인 제안이 본 초안의 미결정 항목을 보완하며, 구현 완료를 뜻하지 않는다.

## 1. 목적

완료된 Hub 작업의 맥락을 대표 기록으로 통합하고, 보조 스레드를 안전하게 아카이브한다.

목록에 보이는 스레드 수와 이후 관리할 맥락의 수를 줄이되, 결정·제약·결과·미해결 사항과 원본 증거를 보존한다. 단순 요약 생성이 아니라 다음 작업이 통합 기록을 찾아 활용하는 것까지 목표로 한다.

아카이브는 영구 삭제가 아니며 저장 공간 감소를 보장하지 않는다. 대화 원문을 물리적으로 병합하거나 모델의 내부 상태를 합치는 기능도 아니다.

## 2. 별도 플러그인과 제품 경계

| 제품 | 책임 |
| --- | --- |
| ThreadHub | 작업 실행, 상태·결과 관리, 관리 스레드의 실행 안전성 및 변경 |
| ThreadGraph | 스레드 관계·충돌·출처 분석 |
| ThreadFold | 분류 정책, 대표 맥락 통합, 정리안·승인·처리 이력 |
| ThreadPort | 세션의 다른 환경 이전. 별도 설계이며 현재 보류 |

ThreadFold는 독립 플러그인으로 구성한다. 다만 Hub 관리 스레드를 직접 변경하는 두 번째 실행 시스템은 만들지 않는다.

- 첫 버전은 Hub 연동이 필수다.
- ThreadGraph는 선택적인 분석 연동이다. 결과는 근거이지 실행 권한이 아니다.
- ThreadFold가 승인된 정리안을 전달하면 Hub 데몬이 상태를 재검증하고 아카이브·복원을 수행한다.
- ThreadFold가 Hub Registry나 Codex 원본 저장소를 직접 수정하지 않는다.
- 통합 기록은 ThreadFold가 버전 있는 로컬 데이터로 소유한다. 원본 작업 상태와 완료 판정은 계속 Hub가 소유한다.
- ThreadPort와 공유·이전 기능을 혼합하지 않는다.

## 3. 배경과 진단 가설

이전 코드 조사에서 완료된 작업 기록이 생성 예산에서 제외되지만 기록 자체는 남고, 복잡한 Run은 영구 오케스트레이터 스레드를 생성하며, 종료 시 자동 아카이브 경로는 ephemeral 스레드에 한정된 것을 확인했다.

따라서 실행 용량 제한과 누적 기록 보존 정책은 별개의 문제다. 이 관찰은 당시 로컬 코드 기준이며 최신 구현과 실제 실행 기록으로 재확인해야 한다. 전체 스레드 증가량이나 고아 수를 실측한 결과는 아니다.

Hub와 연결 정보가 없다고 바로 고아로 판단하지 않는다. 사용자가 직접 만든 대화일 수 있으므로 생성 주체와 범위를 확인하고, 불명확한 대상은 보호한다.

## 4. 첫 버전 범위

### 포함

- 사용자가 선택한 프로젝트의 Hub 생성·관리 스레드 진단
- 완료된 동일 Run 안에서 대표·보조 스레드 식별
- 근거 있는 분류 및 버전 있는 통합 기록
- 정리 미리보기와 명시적 승인
- 적용 직전 안전성 재검증
- 보조 스레드 아카이브, 항목별 결과 기록, 복원
- 이후 Hub 작업의 통합 기록 활용 검증

### 제외

- 영구 삭제 및 대화 원문 물리적 병합
- 백그라운드 자동 정리와 기간 기반 자동 실행
- 사용자 개인 스레드의 임의 처리
- 서로 다른 Run의 주제 유사성만을 근거로 한 자동 통합
- 원본 코드·worktree·결과물 삭제
- 새 오케스트레이터나 중복 작업 상태 관리 시스템

## 5. 현황 진단

선택한 프로젝트의 네이티브 스레드와 Hub Run·Task 정보를 대조한다.

- 생성 주체, 연결된 Run·Task, 프로젝트·브랜치·작업 공간
- 실행·승인 대기·재시도·검증·통합 상태 및 실행권
- 대표 결과 링크, 원본 출처, 결과물·미해결 문제
- 보존 지정과 확인 가능한 사용자 선택
- 재사용·신규 생성·분기 비율 및 재사용하지 못한 이유
- 연결 불명 또는 읽기 실패 항목

전체 수, 보호 대상, 통합 후보, 연결 불명 대상을 관찰 시점과 함께 보고한다. 페이지 누락이나 접근 불가로 전체를 확인하지 못하면 부분 집계임을 표시한다. 이 단계에서는 스레드를 변경하지 않는다.

## 6. 분류 계약

| 판단 축 | 구분 |
| --- | --- |
| 실행 안전성 | 보호 / 정리 가능 / 확인 불가 |
| 맥락 가치 | 대표 / 통합할 고유 정보 / 중복·대체 / 판단 보류 |

분류에는 이유·출처·관찰 시점을 남긴다. 실행 상태나 연결을 확인하지 못하면 정리 가능으로 추정하지 않는다.

### 보호 조건

- 활성 작업 또는 유효한 실행권이 있음
- 승인·재시도·검증·통합·복구 등 후속 처리가 남음
- 미통합·충돌 결과물 등 정리가 끝나지 않은 증거가 있음
- 사용자가 보존하도록 지정함
- 공유 스레드가 다른 활성 Run에도 연결됨
- 상태·원본 내용·참조 의존성을 충분히 확인하지 못함

대표 결과 스레드는 기본적으로 유지한다. 첫 버전은 동일 Run만 통합하되, 안전성 검사는 다른 Run과의 연결도 확인해야 한다.

## 7. 통합 기록 계약

통합 기록에는 다음을 포함한다.

1. 원래 목표와 적용 범위
2. 결정·제약 및 변경된 결정의 이유
3. 적용된 변경·결과물 참조
4. 검증 결과와 증거
5. 실패 원인·미해결 사항·다음 행동
6. 원본 스레드·Turn·결과물 출처
7. 관찰 시점, 원본 버전 또는 지문, 통합 버전, 누락·불확실성

최신 기록이라는 이유로 충돌하는 결론을 정답으로 채택하지 않는다. 관찰 사실과 추론을 구분하고 프로젝트·브랜치·버전 차이를 보존한다.

기존 대표 스레드를 우선 선택한다. 통합 기록은 별도 로컬 데이터로 관리하여 정리할 때마다 새 스레드를 만들지 않는다. 대표 스레드와 통합 기록의 연결·표시 방식은 구현 계약에서 확정한다. 기존 대화에 메시지를 쓰는 것은 자동으로 승인된 것으로 간주하지 않는다.

원본의 결정·제약·미해결 사항·증거가 보존되고 이후 작업에서 접근할 수 있어야 통합 완료로 판단한다. AI의 누락 검사는 완전성을 보장하지 않으므로 원본을 보존하고 검토 가능한 출처를 제공한다.

## 8. 사용자 흐름

예시 요청: “이 프로젝트에서 끝난 작업들을 정리해줘.”

1. 범위를 확인하고 현황을 진단한다.
2. 동일 Run별 대표 기록과 보조 기록을 제안한다.
3. 통합 내용·원본 출처·아카이브 대상·제외 이유를 보여준다.
4. 정리 전후 예상 목록 수와 복원 방법을 안내한다.
5. 사용자는 계획을 수정·거절하거나 승인한다.
6. 안전성 재검증 후 적용하고 항목별 결과를 보고한다.

미리보기만으로 원본 스레드를 변경하지 않는다. 진단 요청 역시 적용 권한이 아니다.

## 9. 적용·복원 계약

적용 순서:

1. 승인된 대상 ID, 계획 버전, 원본 지문, 동작 범위를 고정한다.
2. Hub가 실행 상태·보존 상태·참조를 다시 검사한다.
3. 통합 기록을 저장하고 출처·누락 검증을 완료한다.
4. Hub가 조건을 충족한 보조 스레드만 아카이브한다.
5. 실제 결과를 읽어 확인하고 항목별 처리·복원 정보를 남긴다.

재검증과 변경 사이에 실행이 시작되지 않도록 Hub의 실행권·잠금과 조율한다. 미리보기 후 다시 사용되거나 내용이 바뀐 항목은 제외하거나 재승인을 요구한다. 단순히 일정 시간이 지났다는 이유로 승인 범위를 확대하지 않는다.

네이티브 아카이브가 자손 스레드까지 영향을 줄 수 있는지 확인하고, 예상 영향 집합이 승인·보호 범위와 맞지 않으면 적용을 차단한다. API 성공 응답만으로 모든 항목이 완료됐다고 판단하지 않는다.

외부 아카이브와 로컬 저장은 하나의 원자적 트랜잭션이라고 가정하지 않는다. 항목별 저널, 멱등성 키, 재시도·재조정으로 중간 실패를 처리한다. 복원은 이번 작업에서 실제로 아카이브한 대상과 기존 상태를 기준으로 수행한다.

복원 후 통합 기록은 역사적 버전으로 유지할 수 있지만, 유효·철회·대체 상태를 명시하여 Hub가 잘못 재사용하지 않게 한다. 기존 결과 링크·증거 접근 및 그래프 표시도 확인한다.

## 10. 내부 구성 제안

| 구성 | 책임 |
| --- | --- |
| Inventory Adapter | 스레드와 Hub 상태의 범위 제한 조회 |
| Classifier | 실행 안전성과 맥락 가치의 근거 있는 분류 |
| Consolidator | 버전 있는 통합 기록과 출처 생성 |
| Plan Store | 대상·원본 지문·계획 버전·승인 보존 |
| Hub Adapter | 안전성 검사 및 승인된 아카이브·복원 요청 |
| Operation Journal | 항목별 적용·실패·복원·재조정 기록 |
| Graph Adapter | 선택적인 관계·충돌 분석 결과 활용 |

이 구성은 설계 제안이다. 도구명, 데이터 스키마, Hub 연동 API, 저장소 형식은 구현 전에 계약으로 확정한다. 분석과 적용 도구는 분리하고 실제 부수 효과에 맞는 권한을 선언한다.

## 11. 단계별 계획

### 1단계 — 실제 상태 진단

최신 코드와 선택한 프로젝트의 실제 기록으로 증가 원인과 후보 수를 확인한다.

완료 기준: 전체·보호·후보·불명 대상을 근거와 함께 설명할 수 있음.

### 2단계 — 분류·통합·연동 계약

동일 Run 경계, 보호 규칙, 대표 선정, 통합 기록, Hub 실행권 조율, 승인·복원 계약을 확정한다.

완료 기준: 분류 이유가 추적되고 ThreadFold·Hub·Graph의 상태 소유권이 중복되지 않음.

### 3단계 — 통합 미리보기

원본 변경 없이 대표 기록·통합 내용·정리 대상·제외 이유·예상 감소량을 보여준다.

완료 기준: 사용자가 검토·수정·거절할 수 있음.

### 4단계 — 안전한 적용·복원

명시적 승인, 실행 직전 재검증, 통합 기록 보존, Hub를 통한 아카이브, 항목별 검증·복원을 구현한다.

완료 기준: 활성 스레드 오처리 없이 부분 실패·재시도·복원을 검증함.

### 5단계 — 후속 작업 연동 및 플러그인 패키징

Hub의 다음 작업이 통합 기록을 출처와 함께 활용하도록 연결한다. 독립 플러그인 패키지와 최초 설치·업데이트를 검증한다.

완료 기준: 원본 증거 접근 유지, 실제 맥락 재사용, 설치·업데이트 시 데이터 보존.

### 6단계 — 검증 후 확대

완료된 Run 하나 → 여러 Run → 프로젝트 전체 순으로 확대한다. 첫 버전 검증 후에만 주제별 통합, 보존 기간, 자동 정리를 별도 요구사항으로 검토한다. 생성량·재사용 정책 개선은 Hub의 책임으로 남긴다.

## 12. 필수 테스트와 성공 지표

필수 테스트:

- 실행 재개와 정리 사이의 경합
- 승인 후 원본·보존 상태 변경
- 다른 활성 Run과 공유된 스레드
- 상충하는 결정, 누락된 원본, 미통합 결과물
- 자손에 대한 예상 밖 아카이브 영향
- 통합 기록 저장 후 아카이브 실패 및 그 반대의 불일치 복구
- 프로세스 종료·재실행·중복 요청
- 아카이브 복원 및 결과·증거 링크 접근
- ThreadGraph 미연결·오래된 분석 결과
- 후속 Hub 작업이 올바른 통합 버전을 선택하는지

성공 지표:

- 보호 대상 오처리 0건
- 통합 항목의 출처 추적 가능
- 중요한 결정·제약·미해결 사항 보존
- 기존 결과물·증거 접근 유지
- 목록 감소와 후속 작업의 맥락 재사용 확인
